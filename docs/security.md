# Security boundaries

This is an educational demo with synthetic data. It is not a bank, payment service, security audit, or suitable place for real financial details.

## What is protected

- A randomly generated, meaningless mock session token and the lock preference are stored in EncryptedSharedPreferences. Preference keys use AES256-SIV; values use AES256-GCM. The master key is held in Android Keystore. The token is never sent, logged, or displayed and grants no access to any service.
- Backups are disabled. No credentials, API keys, signing keys, personal account identifiers, analytics, or bank endpoints are included. The debug signing key is generated by the Android build tools, outside Git.
- Optional foreground screen lock uses AndroidX BiometricPrompt (the Android system prompt), allowing strong biometrics or a secure device credential. Enabling and disabling require successful authentication. An enabled app locks on `onStop`, including after backgrounding; process recreation starts locked. Cancellation does not unlock it. A system PIN must be configured before the option becomes available.
- Exact integer cents, server-independent validation, and a Room transaction protect the demo ledger against partial debits and concurrent overdrafts. UI double taps are suppressed while recording.
- The app makes no network requests. Retrofit is exercised against MockWebServer on loopback in tests. Its factory rejects non-loopback hosts. Only the debug variant has INTERNET permission, with cleartext allowed solely for localhost and 127.0.0.1. The release manifest has no INTERNET permission.

## What is not protected

- Room is **not encrypted**. Database, transaction references, and balances are accessible to the app process, a debugger on a debuggable build, and an attacker controlling the device. Android's sandbox/device encryption are not a substitute for an encrypted database.
- The token's key is not gated by per-use biometric authentication. The screen lock is a UI gate, not cryptographic authorization of data access or payments. It does not prevent process tampering, root access, instrumentation, memory inspection, screenshots, or task-switcher previews. No inactivity timer is provided while the app stays in the foreground.
- EncryptedSharedPreferences / security-crypto 1.1.0 is deprecated upstream. It is deliberately used to satisfy this small demo's explicit storage requirement; this is not a recommendation for a new production design. A production design needs a reviewed key lifecycle, encrypted storage strategy, recovery, and threat model.
- No TLS/bank protocol, PSD2, remote authentication, transaction signing, fraud detection, compliance certification, penetration test, production security review, or independent audit exists.
- IBAN checks cover only the nine countries listed in the app: ASCII structure, country length, and MOD-97 checksum. They do not verify national bank/branch rules, ownership, existence, or reachability. Transfers only create local records.
- Clearing app storage/uninstalling deletes the ledger and token; reinstalling seeds the same fictional records. There is no remote recovery or synchronization.

## Verification and limits

JUnit checks validation, category logic, ViewModel errors/concurrency states, and loopback Retrofit success/error handling. Emulator tests check Room persistence and atomicity, Compose form/list interactions, ciphertext rather than plaintext token storage, three app screenshots, and the real device-credential BiometricPrompt flow with background relocking. The latter uses a disposable emulator PIN (`1234`) configured by CI. It is skipped on unsecured devices; the CI report script rejects skipped tests. Biometric sensor enrollment and fingerprint/face hardware success are **not tested**. The PIN is a public test fixture, never an app credential.

See Android's [BiometricPrompt API](https://developer.android.com/reference/androidx/biometric/BiometricPrompt) and [security-crypto release notes](https://developer.android.com/jetpack/androidx/releases/security) for platform behavior and deprecation context.
